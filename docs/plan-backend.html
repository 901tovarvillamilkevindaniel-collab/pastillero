Cinco cavidades, cada una con su LED. Buzzer en GPIO 12, RTC DS1307 en I²C (SDA 21, SCL 22). En el ejemplo, la pastilla 2 está sonando.

Vista general

Tres piezas, una sola regla

La alarma se decide dentro del ESP32, con su reloj RTC. La nube solo sirve para configurar los horarios desde el celular y para ver qué pasó. Así, si se cae el WiFi o Vercel, la pastilla suena igual.

Responsabilidades

Quién hace qué

ESP32

MicroPython · firmware/
  • Lee la hora del DS1307 y la corrige por NTP (hora de Bogotá, UTC−5) cuando hay WiFi.
  • Dispara la alarma: LED de la cavidad y buzzer intermitente.
  • Guarda los horarios en schedules.json (flash).
  • Consulta a Vercel cada 30 s, o cada 5 s mientras suena.
  • Guarda en una cola los eventos que no pudo enviar.

Vercel

Node.js · web/
  • Sirve el panel web para el celular.
  • Tiene las 5 funciones serverless, toda la lógica de la nube.
  • Revisa las claves del dispositivo y del administrador.
  • Es el único que habla con Supabase.

Supabase

Postgres · supabase/
  • Guarda horarios, historial, comandos y estado del dispositivo.
  • Valida los datos con restricciones CHECK.
  • RLS activado sin políticas: nadie entra con la clave pública.
  • Sin Edge Functions. Abajo se explica por qué.
Funciones serverless en Vercel

Cinco endpoints

Dos los llama el ESP32 y se protegen con x-device-key. Tres los llama el panel y se protegen con x-admin-key. Cada función es un archivo dentro de web/api/.

Los llama el ESP32
GET/api/device/sync?ringing=0|1 ESP32 · cada 30 s (5 s si suena)

Es el latido del dispositivo. Devuelve los horarios vigentes y los comandos pendientes, y anota que el ESP32 sigue vivo.

Lee
schedules
Escribe
commands (marca como consumidos), device_status (último contacto, si está sonando)
Regla
Un comando con más de 2 minutos se descarta. Así, un "silenciar" viejo no apaga la alarma del día siguiente.
{
  "schedules": [
    { "slot": 0, "time": "08:00", "active": true },
    { "slot": 1, "time": null,    "active": false }
  ],
  "commands": ["silence"]
}
POST/api/device/events ESP32 · cuando pasa algo

Recibe lo que pasó en el pastillero: la alarma sonó, alguien la silenció o nadie la atendió. Acepta hasta 50 eventos de una vez, para vaciar la cola después de un corte de WiFi.

Escribe
events
Tipos
triggered sonó · silenced confirmada · missed 10 min sin confirmar
{ "events": [
  { "slot": 1, "type": "triggered", "device_time": "2026-11-18 08:00:00" }
] }
Los llama el panel web
GET/api/state Panel · al abrir y cada 10 s

Todo lo que muestra la pantalla: los 5 horarios, si el pastillero está en línea (contacto hace menos de 90 s), si está sonando y los últimos 30 eventos.

Lee
schedules, device_status, events
PUT/api/schedules Panel · botón "Guardar horarios"

Guarda los horarios de las cavidades. Una hora vacía (null) desactiva esa cavidad, algo que el sketch de Arduino no permitía. Rechaza todo lo que no sea HH:MM válido.

Escribe
schedules (upsert por slot)
Llega al ESP32
En la siguiente consulta, como mucho 30 s después.
{ "schedules": [ { "slot": 0, "time": "08:00" }, { "slot": 1, "time": null } ] }
POST/api/silence Panel · botón "Silenciar"

Deja un comando silence en la cola. El ESP32 lo recoge en la siguiente consulta: unos 5 s si está sonando.

Escribe
commands
Código compartido

web/lib/supabase.js crea el cliente con la clave secreta. web/lib/auth.js compara las claves en tiempo constante. web/lib/constants.js guarda las 5 cavidades, el formato de la hora y los tiempos límite.

Supabase

Solo base de datos, sin funciones

Supabase también ofrece funciones serverless (Edge Functions), pero aquí no las usamos. El panel ya vive en Vercel, así que poner la API ahí mismo deja toda la lógica en un solo lugar, con un solo despliegue y una sola copia de las claves. Supabase queda como la base de datos y valida lo básico con restricciones de Postgres.

Flujo 1

Programar un horario desde el celular

sequenceDiagram
  autonumber
  actor F as Familiar
  participant V as Vercel /api
  participant S as Supabase
  participant E as ESP32
  F->>V: PUT /api/schedules, pastilla 1 a las 08:00
  V->>S: upsert en schedules
  S-->>V: ok
  V-->>F: 200, horarios guardados
  Note over E: hasta 30 s después
  E->>V: GET /api/device/sync
  V->>S: lee schedules, consume commands, actualiza device_status
  V-->>E: schedules con 08:00
  E->>E: guarda schedules.json en la flash
Flujo 2

Suena la alarma y se silencia

sequenceDiagram
  autonumber
  participant E as ESP32
  participant V as Vercel /api
  participant S as Supabase
  actor F as Familiar
  E->>E: el RTC marca 08:00 y coincide con la pastilla 1
  E->>E: LED GPIO 23 y buzzer encendidos

  V->>S: insert en events
  Note over E: consulta cada 5 s mientras suena

  V-->>F: sonando, pastilla 1
  alt alguien pulsa Silenciar
    F->>V: POST /api/silence
    V->>S: insert en commands
    E->>V: GET /api/device/sync?ringing=1
    V->>S: marca el comando como consumido
    V-->>E: commands silence
    E->>E: apaga LED y buzzer
    E->>V: POST /api/device/events, silenced
  else nadie responde en 10 minutos
    E->>E: apaga el buzzer, el LED sigue encendido
    E->>V: POST /api/device/events, missed
  end
Flujo 3

Sin internet

sequenceDiagram

  participant V as Vercel /api
  Note over E,V: el WiFi se cae

  E->>E: a las 08:00 suena igual, por el RTC

  V-->>E: horarios al día
Límite conocido

Sin internet, el panel no puede silenciar la alarma. El buzzer se apaga solo a los 10 minutos y el evento queda marcado como missed. Si más adelante queremos silenciar sin red, la solución es un botón físico, que sería un cambio de hardware.

Seguridad

Dónde vive cada clave

ClaveDónde estáQué abre
DEVICE_KEYVariables de entorno de Vercel y firmware/config.py (fuera de git)Solo los dos endpoints /api/device/*
ADMIN_KEYVariables de entorno de Vercel. Se escribe una vez en el panel y el navegador la recuerdaLos endpoints del panel
SUPABASE_SECRET_KEYSolo en las variables de entorno de VercelToda la base de datos. Nunca va al ESP32 ni al navegador
SUPABASE_URLVariables de entorno de VercelNo es secreta

El ESP32 usa HTTPS sin verificar el certificado, igual que setInsecure() en Arduino. El tráfico va cifrado, pero alguien dentro de tu misma red WiFi podría hacerse pasar por Vercel. Para un pastillero en casa es aceptable. Si después hace falta, se le carga al ESP32 el certificado raíz.

Orden de trabajo

Paso a paso

  1. Prueba de hardware en MicroPython

    Encender los 5 LEDs, hacer sonar el buzzer y leer el DS1307 desde PyCharm. Todavía sin red.

  2. Base de datos en Supabase

    Crear el proyecto y correr schema.sql. Revisar que RLS esté activo.

  3. API en Vercel

    Los 5 endpoints y las variables de entorno. Probarlos con curl antes de tocar el ESP32.

  4. Panel web

    Horarios, botón de silenciar, estado en línea e historial, pensado para el celular.

  5. Firmware conectado

    WiFi, hora por NTP, consultas a Vercel, cola de eventos y horarios guardados en la flash.

  6. Prueba de punta a punta

    Una alarma a 2 minutos: silenciarla desde el celular, dejar que otra se pierda y desconectar el WiFi para ver que suena igual.
