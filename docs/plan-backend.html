Cinco cavidades, cada una con su LED. Buzzer en GPIO 12. Sin módulo RTC: la hora la manda Vercel. En el ejemplo, la pastilla 2 está sonando.

Vista general

Tres piezas, una sola regla

La alarma se decide dentro del ESP32, con su reloj interno. Vercel le manda la hora de Bogotá en cada consulta, y además sirve para crear las alarmas desde el celular, confirmar las tomas y ver qué pasó. Si se cae el WiFi o Vercel, la pastilla suena igual mientras el ESP32 no pierda la corriente.

Responsabilidades

Quién hace qué

ESP32

MicroPython · firmware/
  • Pone en hora su reloj interno con la hora de Bogotá que le manda Vercel.
  • Dispara la alarma: LED de la cavidad y buzzer intermitente.
  • Guarda las alarmas en alarms.json (flash) y revisa el día de la semana.
  • Consulta a Vercel cada 30 s, o cada 5 s mientras suena.
  • Guarda en una cola los eventos que no pudo enviar.

Vercel

Node.js · web/
  • Sirve el panel web para el celular.
  • Da la hora: la calcula en la zona America/Bogota y se la manda al ESP32.
  • Tiene las funciones serverless (7 endpoints), toda la lógica de la nube.
  • Revisa las claves del dispositivo y del administrador.
  • Es el único que habla con Supabase.

Supabase

Postgres · supabase/
  • Guarda alarmas, historial, comandos y estado del dispositivo.
  • Valida los datos con restricciones CHECK.
  • RLS activado sin políticas: nadie entra con la clave pública.
  • Sin Edge Functions. Abajo se explica por qué.
Funciones serverless en Vercel

Siete endpoints

Dos los llama el ESP32 y se protegen con x-device-key. Cinco los llama el portal y son de acceso libre: no piden clave. Cada función es un archivo dentro de web/api/.

Los llama el ESP32
GET/api/device/sync?ringing=0|1 ESP32 · cada 30 s (5 s si suena)

Es el latido del dispositivo. Devuelve la hora de Bogotá, las alarmas activas y los comandos pendientes, y anota que el ESP32 sigue vivo.

Lee
alarms (solo las activas)
Escribe
commands (marca como consumidos), device_status (último contacto, si está sonando)
Regla
Un comando con más de 2 minutos se descarta. Así, un "silenciar" viejo no apaga la alarma del día siguiente.
Hora
Vercel la manda como segundos desde 1970 (epoch) más el desfase de Bogotá (−300 min). El ESP32 ajusta su reloj con cada respuesta. El viaje por la red le resta 1 a 2 s, que no importa para alarmas por minuto.
{
  "clock": { "epoch": 1795006800, "utc_offset_min": -300, "local": "2026-11-18T08:00:00-05:00" },
  "alarms": [
    { "id": 1, "slot": 0, "time": "07:00", "days": [1,2,3,4,5,6,7] },
    { "id": 5, "slot": 3, "time": "09:00", "days": [7] }
  ],
  "commands": ["silence"]
}
POST/api/device/events ESP32 · cuando pasa algo

Recibe lo que pasó en el pastillero: la alarma sonó, alguien la silenció o nadie la atendió. Acepta hasta 50 eventos de una vez, para vaciar la cola después de un corte de WiFi.

Escribe
events
Tipos
triggered sonó · silenced tomada (confirmada en el celular) · missed 10 min sin confirmar
{ "events": [
  { "alarm_id": 1, "slot": 0, "type": "triggered", "device_time": "2026-11-18 07:00:00" }
] }
Los llama el portal
GET/api/state Portal · al abrir y cada 10 s

Todo lo que muestra la pantalla: las alarmas, si el pastillero está en línea (contacto hace menos de 90 s), si está sonando y los últimos 30 eventos.

Lee
alarms, device_status, events
POST/api/alarms Portal · modal "Nueva alarma"

Crea una alarma: compartimento, medicamento, hora y días. Un mismo compartimento puede tener varias alarmas al día, pero no dos a la misma hora. Máximo 20 alarmas.

Escribe
alarms
Llega al ESP32
En la siguiente consulta, como mucho 30 s después.
{ "slot": 0, "time": "07:00", "label": "Losartán 50 mg", "days": [1,2,3,4,5,6,7], "active": true }
PUT/api/alarms/:id Portal · editar o interruptor

Cambia una alarma. Acepta cambios parciales: el interruptor de la lista solo manda { "active": false }.

Escribe
alarms (updated_at se actualiza solo)
DELETE/api/alarms/:id Portal · "Eliminar" (doble toque)

Borra la alarma. Su historial se conserva: los eventos quedan con alarm_id vacío y guardan el compartimento.

Escribe
alarms
POST/api/silence Portal · botón "Ya se la tomó"

El pastillero no tiene sensor para saber cuándo se saca la pastilla, así que la toma se confirma desde el celular. Deja un comando silence en la cola; el ESP32 lo recoge en unos 5 s, se calla y registra el evento silenced.

Escribe
commands
Código compartido

web/lib/supabase.js crea el cliente con la clave secreta. web/lib/auth.js compara las claves en tiempo constante. web/lib/constants.js guarda los 5 compartimentos, el formato de la hora, el máximo de alarmas y los tiempos límite.

Supabase

Solo base de datos, sin funciones

Supabase también ofrece funciones serverless (Edge Functions), pero aquí no las usamos. El panel ya vive en Vercel, así que poner la API ahí mismo deja toda la lógica en un solo lugar, con un solo despliegue y una sola copia de las claves. Supabase queda como la base de datos y valida lo básico con restricciones de Postgres.

Límite conocido

Sin internet, el panel no puede silenciar la alarma. El buzzer se apaga solo a los 10 minutos y el evento queda marcado como missed. Si más adelante queremos silenciar sin red, la solución es un botón físico, que sería un cambio de hardware.

Límite por no tener RTC

Si se va la luz y vuelve sin internet, el ESP32 no sabe qué hora es y no puede disparar alarmas hasta que se conecte a Vercel. Mientras tanto, los 5 LEDs parpadean despacio para avisar que está "sin hora". Las alarmas no se pierden porque están en la flash.

Seguridad

Dónde vive cada clave

ClaveDónde estáQué abre
DEVICE_KEYVariables de entorno de Vercel y firmware/config.py (fuera de git)Solo los dos endpoints /api/device/*
PortalSin clave: acceso libre para quien tenga la URLCrear, editar, borrar y silenciar alarmas

SUPABASE_URLVariables de entorno de VercelNo es secreta

El ESP32 usa HTTPS sin verificar el certificado, igual que setInsecure() en Arduino. El tráfico va cifrado, pero alguien dentro de tu misma red WiFi podría hacerse pasar por Vercel. Para un pastillero en casa es aceptable. Si después hace falta, se le carga al ESP32 el certificado raíz.

Orden de trabajo

Paso a paso

  1. Prueba de hardware en MicroPython

    Encender los 5 LEDs y hacer sonar el buzzer desde PyCharm. Todavía sin red.

  2. Base de datos en Supabase · hecho

    Tablas alarms, events, commands y device_status creadas con RLS. La clave pública no puede leer nada.

  3. API en Vercel

    Los 5 endpoints y las variables de entorno. Probarlos con curl antes de tocar el ESP32.

  4. Portal web · diseño hecho

    Alarmas con modal, confirmar toma, estado en línea e historial. Falta conectarlo a la API.

  5. Firmware conectado

    WiFi, hora desde Vercel, consultas, cola de eventos y alarmas (con días) guardadas en la flash.

  6. Prueba de punta a punta

    Una alarma a 2 minutos: silenciarla desde el celular, dejar que otra se pierda y desconectar el WiFi para ver que suena igual. Por último, reiniciarlo sin red para ver el aviso de "sin hora".
